## 项目分析与任务派发

**第一步：智能分析项目结构。** 快速浏览 {target_work_dir} 的目录结构、文件规模、技术栈特征，评估代码体量（文件数、代码行数），形成项目概览。

**第二步：制定派发策略。** 根据项目体量决定识别方式：

- **小项目**（< 50 文件，目录 ≤ 2 层）：单次完整识别即可
- **中等项目**（50-200 文件，目录 3-4 层）：按顶层模块/子系统划分批次，分批识别
- **大项目**（> 200 文件，或目录 ≥ 5 层）：按子目录派发子任务，每个子任务独立识别该子目录的攻击面，最后汇总

**派发原则**：

- 派发粒度按子目录/模块划分，各子任务的扫描范围**不重叠**
- 优先识别含入口/路由/监听/调度/执行器语义的目录（`controller/`、`api/`、`handler/`、`listener/`、`scheduler/`、`service/`、`consumer/`、`job/`、`task/`、`endpoint/`、`router/`、`cmd/` 等），再扫其他
- 各子任务产出统一格式的 surface 文件，写入 {target_work_dir}/.vuln_agent_output/discovered_surfaces/
- 子任务数过多时可聚合（如先按顶层 5 个大目录派发，每个大目录内部再按需细分）

**智能判断依据**（辅助评估派发策略）：

- 项目使用的技术栈（Spring Boot / Django / Express / Gin 等框架特征）
- 目录命名规律（是否按业务模块组织、是否按功能层组织）
- 入口文件位置（main 启动类、路由配置等）
- 配置文件中的模块划分线索

**记录执行计划**（可选）：将派发策略简要记录到 {target_work_dir}/.vuln_agent_output/meta/collect-plan.md，便于后续审查追溯。

## 识别范围

收集所有攻击面（接口 + 非接口）：

- **接口**：web（REST / JAX-RS / Servlet / GraphQL）、MQ 消费者、gRPC、WebSocket / SSE — 识别 REST API 暴露面时可使用 `rest-api-extractor` skill 辅助分析。GraphQL：查找 `schema.graphqls` / `graphql` 目录、`@GraphQLController`、`RuntimeWiring`、`graphql-java` 及相关配置。gRPC：查找 `.proto` 文件、`@GrpcService` 注解、protobuf 配置
- **非接口**：独立可执行脚本、独立工具（含 main 入口的可执行程序）、定时任务、CLI 命令入口

每条目必须提取精确的**来源信息**（完整文件路径:行号、函数名），路径必须是完整的绝对或相对项目根路径，供后续分析步骤直接使用。**REST 接口必须找到实际的 Controller 入口代码位置（文件路径:行号:函数名），而非路由配置或接口文档来源。**

分类区分：
- **SCRIPT**：以解释器直接运行的非编译型脚本（.sh / .py / .js 无独立编译构建）
- **TOOL**：需要编译/打包的可独立执行程序（Go/Java/C main 等）
- **"独立工具"**指有 main 函数作为入口的可独立执行的程序，不是编译产物分析也不是工具类/工具函数。

填写输出格式中各字段时，以入口文件及直接可见注解中可获取的信息为主；参数详情需跨文件查阅 DTO 定义的可标注 `（详见 {DTO路径}）`，不强制深追。

识别过程中如果看到值得注意的关键信息（如涉及高危操作、参数来源是用户输入等），**必须**在对应条目的 `**发现**` 字段中客观记录。限于入口处的直接可见信息——但参数来源于外部请求（path/query/body/header）这个事实本身即使不在本文件定义也能判断，应记录。

**识别排除项**：
- 纯框架启动入口（如 `@SpringBootApplication` main、Django manage.py、Gin/Express main()、Flask app.run() 等）不计为攻击面（仅框架启动入口，无业务逻辑）
- 纯工具类/工具函数不计为攻击面（无独立入口）

**无框架项目缺省策略**：不含明显框架特征的项目，按文件入口特征识别（main 函数、`if __name__ == '__main__'`、路由注册语义的配置等）。无法归类的按目录功能命名判断。

## 输出格式

每发现一个攻击面，在 {target_work_dir}/.vuln_agent_output/discovered_surfaces/ 下创建一个文件，命名规则：

```
{target_work_dir}/.vuln_agent_output/discovered_surfaces/{type}-{category}-{slug}.md
```

- `{type}` = `iface`（接口）或 `noniface`（非接口）
- `{category}` = REST / MQ / SCRIPT / TOOL / CRON / CLI 等
- `{slug}` = 简短英文标识，小写字母+连字符

文件内容格式包含**通用字段**和**按分类的补充字段**：

通用字段（所有类型必填）：

```markdown
# 攻击面条目

- **类型**：iface（或 noniface）
- **分类**：REST（或 SCRIPT 等）
- **来源**：/src/main/java/com/acme/UserController.java:48 list()
- **描述**：查询用户列表
- **发现**：（必填，无特殊情况填"无"）入口处直接可见的安全隐患信号，如参数拼接到文件路径/命令字符串、参数未做任何校验、涉及高危操作（文件写、命令执行、外呼等）
```

按分类的补充字段（根据实际类型选填对应的字段集）：

| 分类 | 补充字段 |
|------|---------|
| REST | `**URL**`：`GET /api/users/{id}`、`**入口**`：`src/main/java/com/acme/UserController.java:48 listUsers()`、`**参数**`：path: id, query: page |
| MQ | `**队列/Topic**`：order.created、`**消费者**`：OrderHandler.onCreated() |
| gRPC | `**服务**`：UserService、`**方法**`：GetUser、`**Proto**`：user.proto |
| WebSocket | `**端点**`：/ws/chat、`**处理器**`：ChatHandler |
| GraphQL | `**类型**`：Query/Mutation、`**字段**`：users、`**Resolver**`：UserResolver |
| SCRIPT | `**脚本名**`：backup.sh、`**语言**`：bash、`**入口**`：/opt/scripts/backup.sh |
| TOOL | `**工具名**`：agent、`**语言**`：Go、`**入口**`：/opt/app/cmd/agent/main.go:15 main() |
| CRON | `**表达式**`：`*/5 * * * *`、`**命令**`：/opt/app/healthcheck.sh、`**文件**`：/etc/cron.d/healthcheck |
| CLI | `**命令名**`：agent、`**入口**`：/opt/app/cli/main.go:8 main() |

补充字段如实填写，没有的信息不写，不要编造。

`slug` 为文件名去掉 `.md` 后缀，如 `REST-api-users-list.md` 的 slug 为 `REST-api-users-list`。
