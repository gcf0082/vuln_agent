## 分析点枚举方法

根据分析文件描述的内容判断，不要扫描代码。

**以敏感操作为锚点逆向枚举**：分析点不是从风险模式清单正向匹配出来的，而是从分析文件记录的敏感操作反推出来的。对文件中记录的每个敏感操作（命令执行、SQL、文件读写、HTTP 出站、加解密、解压、端口监听等），逐一反问三个问题：

1. **可控源** — 是否存在攻击者可控制的输入（请求参数、外部系统返回、用户可写存储）？
2. **可达路径** — 该输入是否可能沿调用链到达这个敏感操作？
3. **防护状态** — 文件描述中该操作前是否存在校验/过滤，其实现是否可见？

三个问题都有肯定迹象 → 标记为分析点。任何敏感操作不允许凭"看起来安全"跳过反问过程——漏标分析点意味着该点永远不会被分析，是漏报的源头。

非输入型危险行为（配置缺陷、弱加密、硬编码凭据、敏感信息写日志、内存安全、资源处理不当等）不适用"可控源"反问，改问：危险行为是否存在？触发条件是否现实？有无补偿控制？——有肯定迹象同样标记为分析点。

模式清单与规则索引作为**兜底核对**：枚举完成后对照一遍，命中但未被反问过程覆盖的，补标为分析点。

## 优先级判定规则

1. **高优先级** — 满足以下任一条件：
   - 三要素初步均成立：存在高风险操作、有可控源、从给定信息看**无有效校验/过滤**，初步判断疑似存在安全漏洞
   - 文件中描述了配置类问题：不安全协议、未校验证书、弱加密算法、硬编码认证凭据等
   - 匹配 `{tool_dir}/references/vuln_rules_index.md` 中的模式
   - **C/C++ 内存安全**：如果分析对象是 C/C++ 项目，且描述了内存分配/释放操作（malloc、calloc、realloc、new、delete 等），标记为高优先级分析点

2. **中优先级** — 防护要素存在但有效性待证伪：文件中描述了高风险操作，但从给定信息看**有明显的校验/过滤**，初步判断疑似安全，需深度数据流追踪确认校验是否可绕过

3. **低优先级** — 文件中无高风险操作，但有其他低危问题（如开放重定向、信息泄露、不安全的随机数等）

**分析深度**：高/中优先级需深度数据流追踪，低优先级标准分析即可。

## 输出格式

将评估结果写入 `{target_work_dir}/.vuln_agent_output/vuln_plans/{surface_stem}/` 目录下。

### 有分析点

每个分析点独立一个文件，从 1 开始编号，按优先级命名：

#### high-risk-1.md

```markdown
# 深度分析计划 — {surface_stem} — 命令注入

**优先级**：高
**敏感操作位置**：{文件路径:行号}
```

#### medium-risk-1.md

```markdown
# 深度分析计划 — {surface_stem} — SSRF

**优先级**：中
**敏感操作位置**：{文件路径:行号}
```

#### low-risk-1.md

```markdown
# 分析计划 — {surface_stem} — 开放重定向

**优先级**：低
**敏感操作位置**：{文件路径:行号}
```

### 无任何分析点

仅当不存在任何分析点（高/中/低）时，写入 `low-risk-1.md`，进行通用未知漏洞分析：

```markdown
# 分析计划 — {surface_stem} — 通用未知漏洞分析

**优先级**：低
**任务**：对该攻击面的所有外部输入参数，追踪其到敏感操作的完整数据流，检查是否存在安全漏洞。
```

**仅当业务代码特别简单**（如仅几行代码、无实质业务逻辑）时，写入 `none-risk-1.md`：

```markdown
# 分析计划 — {surface_stem}

**结果**：无需分析
**说明**：业务代码特别简单，无分析价值。
```

## 重要规则

- 每个文件原则上只包含一个分析点；但当多个分析点比较简单时（如同一参数的同类风险、同一函数的多个低危问题），可合并到一个文件中以减少任务数量
- 不要编造不存在的风险
- 仅分析当前攻击面文件描述的内容，不要扩大范围
