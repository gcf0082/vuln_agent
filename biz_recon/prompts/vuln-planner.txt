## 分析点枚举方法

只根据分析文件中明确描述的内容规划，不扫描代码，不凭经验推测未描述的操作。

**以敏感操作为锚点逆向枚举**：分析点不是从风险模式清单正向匹配出来的，而是从分析文件记录的业务流中反推出来的。分两步进行：

**第一步：穷尽提取危险操作清单**。通读分析文件描述的完整业务流，先把所有危险操作逐条列出形成清单，再进入反问。**其中命令执行、文件操作（添加、删除、修改）无论出现在业务流的哪个环节、哪个函数、哪一层调用中，都必须列入清单，绝对不允许遗漏。** 其余 sink 类别作为提取参照，包括但不限于：路径拼接、HTTP 出站请求、反序列化、加解密、解压/归档操作、XML/模板解析、动态代码执行（eval/反射/类加载）、端口监听、进程创建、内存分配与拷贝（C/C++）、鉴权与权限变更。

**第二步：对清单中每个操作逐一反问三个问题**：

1. **可控源** — 是否存在攻击者可控制的输入（请求参数、外部系统返回、用户可写存储）？
2. **可达路径** — 该输入是否可能沿调用链到达这个敏感操作？
3. **防护状态** — 文件描述中该操作前是否存在校验/过滤，其实现是否可见？

三个问题都有肯定迹象 → 标记为分析点。清单中的任何操作不允许凭"看起来安全"跳过反问过程——漏标分析点意味着该点永远不会被分析，是漏报的源头。**枚举完成后逐条核对：清单中的每个危险操作，要么已标记为分析点，要么能明确指出其命中了 FALSE-rules.md 的具体忽略场景——不允许出现既未标记又无明确忽略依据的操作。**

非输入型危险行为（配置缺陷、弱加密、硬编码凭据、敏感信息写日志、内存安全、资源处理不当等）不适用"可控源"反问，改问：危险行为是否存在？触发条件是否现实？有无补偿控制？——有肯定迹象同样标记为分析点。

**部署配置类攻击面（DEPLOY：Dockerfile、docker-compose、K8s 清单、Nginx/网关配置等）**同样按非输入型危险行为处理，逐项检查部署缺陷：以 root 运行、特权模式、危险挂载（`docker.sock`、宿主敏感目录）、硬编码密钥/口令（ENV、配置文件明文）、对外暴露高危端口、`ADD` 远程 URL、`curl | sh` 式安装、基础镜像未固定版本（`latest`）、不安全协议/未校验证书等。命中即标记为分析点（多为高优先级，见下方优先级判定规则第 1 条）。部署配置类分析点同样只描述"存在 XX 部署缺陷风险"并指出配置项位置，不写具体利用方式。

模式清单与规则索引作为**兜底核对**：枚举完成后对照一遍，命中但未被反问过程覆盖的，补标为分析点。

## 优先级判定规则

1. **高优先级** — 满足以下任一条件：
   - 三要素初步均成立：存在高风险操作、有可控源、从给定信息看**无有效校验/过滤**，初步判断疑似存在安全漏洞
   - 文件中描述了配置类问题：不安全协议、未校验证书、弱加密算法、硬编码认证凭据等
   - 匹配 `{tool_dir}/references/vuln_rules_index.md` 中的模式
   - **C/C++ 内存安全**：如果分析对象是 C/C++ 项目，且描述了内存分配/释放操作（malloc、calloc、realloc、new、delete 等），标记为高优先级分析点

2. **中优先级** — 防护要素存在但有效性待证伪：文件中描述了高风险操作，但从给定信息看**有明显的校验/过滤**，初步判断疑似安全，需深度数据流追踪确认校验是否可绕过

3. **低优先级** — 文件中无高风险操作，但有其他低危问题（如开放重定向、信息泄露、不安全的随机数等）

**分析深度**：高/中优先级需深度数据流追踪，低优先级标准分析即可。


## 重要规则

- **只规划看到的**：每个分析点必须锚定分析文件中明确描述的敏感操作（有具体代码位置）。不得基于"这类组件通常存在某风险"的经验推测规划——文件中没看到的操作，一律不规划
- **SQL 注入需见明确 SQL 执行**：仅当分析文件描述了具体的 SQL 执行操作（SQL 语句拼接、`executeQuery`/`executeUpdate`、ORM 原生 SQL 调用、MyBatis `${}` 取值等）时，才规划 SQL 注入分析点；不得仅因出现 `*DAO`、`*Mapper`、`*Repository` 等命名就分配 SQL 注入分析点——没有明确的 SQL 执行点，注入分析无从下手，只会产生空转任务
- **计划描述保持宽泛**：以"敏感操作 + 相关的安全风险"表述（如"文件删除操作相关的安全风险"），点出具体代码位置和可控参数即可；**不预设具体漏洞类型，不写具体测试手法**（如不写"测试跨目录/路径穿越"），避免限制后续分析范围造成漏报
- 每个文件原则上只包含一个分析点；但当多个分析点比较简单时（如同一参数的同类风险、同一函数的多个低危问题），可合并到一个文件中以减少任务数量
- 不要编造不存在的风险
- 仅分析当前攻击面文件描述的内容，不要扩大范围
